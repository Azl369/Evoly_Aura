# 架构设计

状态：候选架构；P0 通过后固定首个可运行版本。

## 总体结构

常驻端采用 C++20 / Win32，Direct2D / DirectWrite 负责绘制。
是否使用 DirectComposition、何种透明窗口组合，由最小原型测量决定。
优先 Windows 11 x64；Win10、ARM64 支持后置，另行评估与记录。

~~~text
用户操作 / 系统事件
        |
WindowsHost -----> PanelController -----> LayoutEngine / WidgetModel
        |                  |                        |
Tray / Hotkeys        EventScheduler           Persistence
                           |
                    RenderCoordinator
                           |
             SharedDevice / Text / IconCache
                           |
             按需分配的面板绘制表面
~~~

## 边界与依赖方向

- core 保持平台无关；处理坐标、面板状态、吸附和刷新决策。
- platform/windows 把系统事件转换为内部事件，不承担组件业务。
- render 消费面板快照；不直接读取磁盘或发网络请求。
- widgets 拆分轻量数据模型与数据提供者。
- persistence 接收配置快照，处理格式版本和写入。
- apps/host 组装模块并负责进程生命周期。

单个常驻进程管理全部基础面板；一个面板不是一个进程。
可使用多个小 HWND；同一进程共享绘图设备与可共享资源。
每个窗口仍有自己的表面与系统管理成本，P0 必须记录随窗口数量的增长。

## 窗口状态

PanelState 保存 id、组件类型、逻辑坐标、尺寸、显示器标识、桌面/HUD 模式、
可见性、锁定状态、主题引用；原生句柄仅在平台模块持有。

模式切换保留业务模型，平台层按需要重建窗口相关资源。
操作附带版本序号，避免旧异步任务覆盖新状态，这是 Evoly 可以复用的交互经验。
异常时恢复可见窗口或托盘入口，避免透明且不可操作的状态。

桌面挂载后端单独封装。常见 WorkerW / Progman 技巧不能视为稳定的公开 Shell 合同；
必须验证 Explorer 重启、显示桌面、虚拟桌面、Windows 更新和窗口层级。
失败时回退到可控制的普通 / HUD 窗口并提示当前状态。

## 线程与调度

- 一个 UI / 消息循环线程维护窗口和面板状态。
- 一个共享调度器管理到期任务，不给每个组件创建永久线程。
- 阻塞 IO 和图片处理使用受限工作队列；任务支持取消。
- COM / Shell / 渲染对象遵守各自线程亲和与资源生命周期约束。
- 图片解码峰值、网络响应大小与同时处理的任务数有上限。
- 静止时阻塞等待事件，无持续主循环绘制。

## 数据与配置

初期使用小规模、版本化 JSON；布局数据不需要引入 ORM。
格式校验后写入临时文件，再原子替换，并保留上一份可用备份。
损坏时回退备份或默认布局，不执行配置指定的任意命令。
便签持久化独立处理；用户文本不写入公开日志。
数据规模达到明确需求后再评估 SQLite。

## 编辑器与扩展

简单设置优先原生控件。复杂编辑器可以后续拆为按需进程，
经有大小限制、版本校验的本地 IPC 提交配置，关闭后真正退出。

内置组件通过编译期注册；主题与布局使用受约束数据。
外部网页 / 脚本组件属于另一个资源和安全边界，不进入低内存首版基线。
需要隔离的第三方插件将来可以使用独立进程，不能为省内存默认加载任意 DLL。

## 必须原型验证

1. 桌面挂载与透明 / 圆角 / 背景材质的组合。
2. 多小窗口与局部聚合渲染的成本；避免直接选全屏大画布。
3. GPU 初始化基础成本、表面缓存与 DWM 增量。
4. 中文字体、DPI、输入、键盘焦点和无障碍的实现成本。
